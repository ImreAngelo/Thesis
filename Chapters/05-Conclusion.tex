\chapter{Conclusion and Future Work}
\label{chp:conclusion}

This thesis set out to establish what \gls{spar} costs to run. Answering that required first building the \gls{rgsw} products it depends on for BGV-\gls{rns}, where the digit decomposition they are defined over does not exist, and then implementing and measuring the protocol on top of them.

The first section below states what the measurements show about the protocol's practicality and where its limits lie. The second collects the optimizations and extensions that the implementation leaves open, several of which we expect to change the picture materially.

\section{Future Work}
\begin{itemize}
    \item BGV SIMD capabilities \cite{cryptoeprint:2011/133} not utilized in write loop; \texttt{Server::Write} can perform $N$ rounds simultaneously, but does this translate into higher throughput? A constant polynomial is the same object in \gls{simd} batching and as a regular polynomial, so if write is changed to output binary $\{0,1\}$ it should be possible with:
    \begin{itemize}
        \item For each $i \in [0, N)$
        \item mask $\gets e_i = (0,0,\dots, 1, \dots, 0)$ where only the $i$-th element is 1
        \item isolated $\gets h \cdot \text{mask}$
        \item msg
    \end{itemize}
    \item AVX512 not tested because time + no access to a computer that supports this instruction set; this would decrease the RNS primes to 48 bits, increasing performance and security, decreasing noise headroom
    \item RGSW/packed RLWE bandwidth optimization; originally planned, dropped due to time constraints, requires more complicated setup phase as $\rgsw{s}$ is required \cite{chillotti:onionring:2019, cryptoeprint:2025/1088}
    \item BFV implementation should be easy as the library sits on top of OpenFHE, it should be as easy as swapping out a few lines of code. Since BFV places its messages in the most significant bits, the decomposition gadget could be made inexact as with the powers of base, the least significant digits are dropped when $\ell$ is too small for $B^\ell$ to cover $q$
    \item The full sPAR protocols contains additional things such as equivocation protection, sorting buckets etc.
    \item Data per message = $N\log(t)/8 \approx 16385 \cdot (16)/8 = 32770$ bytes $\approx 32$ Kb
    \item sPAR data per msg = $2048 * 8/8 = 2048 = 2$ Kb
    \item If larger params is 16 times slower than expected, throughput is the same
\end{itemize}
