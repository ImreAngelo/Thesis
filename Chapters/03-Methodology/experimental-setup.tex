\section{Experimental Setup}

\subsubsection{sPAR}
We do not separate the workload of the clients and server onto separate physical machines. Instead a single all-knowing orchestrator, holding the joint secret key, performs the setup and one full round. Multi-party \gls{fhe} is still employed throughout: the orchestrator separates its \emph{virtual} users, each generating their own private key share and a corresponding public share, and the public shares are synthesized into one joint public key.

The orchestrator takes the number of users $\eta$ as input and gives each user a unique identifier. Every user encrypts its identifier under the joint key and sends it to the server together with three random indices, and once all messages have been received the server performs the write operation on each of them. The setup phase is considered free, as it is static and involves no communication in the simulation.

\subsubsection{Measurement and Validation}
Timings are collected with Google Benchmark and correctness is checked with GoogleTest. Each benchmark runs $10$ repetitions, and every repetition continually repeats the operation within a span of one second. Operations taking longer than a second therefore yield at least $10$ samples and the faster functions yield hundreds, in both cases with a low coefficient of variation. 

% The two serve different purposes. Benchmarks are optimized for speed and perform no correctness checks, which could otherwise affect the measurement. Each function only needs to run once, since the total time can be extrapolated: client encryption and decryption are run independently by each user and the final decryption is a single aggregation, so the one-shot runtime \textit{is} the runtime, and for the server write only the per-user runtime is of interest. Unit tests are not optimized for speed and instead repeat slow correctness checks at several levels, so that a failure reports not only that an operation failed but \textit{where} and why. Because both share the same parameters and code, a passing test empirically validates the correctness of what the benchmarks measure.

\subsubsection{Noise Analysis}
% As the clients are simulated
The testing environment always has access to the secret key, so the error of an \gls{rlwe} ciphertext is checked directly.
\begin{gather}
    x = (c_0, c_1) = (c_1s + \Delta m + \epsilon, c_1) \\
    \implies \epsilon = c_0 - c_1s - \Delta m, \quad m = \Call{Decrypt}{x, s}
\end{gather}
An \gls{rgsw} ciphertext is an intermediate object, not meant to be decrypted. To get a representative measure of the noise, we convert the \gls{rgsw} to an \gls{rlwe} ciphtext and measure its noise as above. Since the gadget vector usually contains $1$ as an element, one of the \gls{rgsw} rows are an \gls{rlwe} of the actual unscaled message. Alternatively, one can compute the external product using a public key \Call{RLWE}{0}. We use the latter method, as the former ignores the errors of the other rows.

\subsubsection{Multi-Threaded Performance}
\label{sec:amdahl}
The main advantage \gls{rns} holds over classical single-precision representations is its multi-threading capability. As described above, our implementation allows efficient parallelization over $k\ell$ threads. However, if fewer threads are available during benchmarking, we extrapolate the expected performance at $k\ell$ processors by modeling theoretical scaling behavior using Amdahl's Law~\cite{Gustafson:2011}.

\begin{definition}[Amdahl's Law]
    A task whose execution is divided into a strictly serial fraction $f$ and a broadly parallelizable fraction $1-f$ will experience a theoretical speedup over $T$ processors given by:
    \begin{equation}
        \label{eq:amdahl}
        \frac{1}{f + \frac{1-f}{T}}
    \end{equation}
\end{definition}

Let $E(T)$ denote the total execution time of the algorithm on $T$ threads. Because speedup is defined as $\frac{E(1)}{E(T)}$, we can substitute this ratio into~\eqref{eq:amdahl} and isolate $E(T)$ to form a linear equation:

\begin{equation}
    \label{eq:amdahl-et}
    E(T) = E(1)f + \frac{E(1)(1-f)}{T}
\end{equation}

By mapping \eqref{eq:amdahl-et} to the variables $y = E(T)$ and $x = \frac{1}{T}$, the relationship resolves into a standard linear model $y = \beta_0 + \beta_1 x$. The intercept $\beta_0 = E(1)f$ represents the fixed serial execution time, while the slope $\beta_1 = E(1)(1-f)$ captures the parallelizable workload scaled by the inverse thread count.

\newpage
By measuring empirical execution times across a limited set of processor counts ($T = 1, 2, 3, \dots, T_{max}$), we can perform an ordinary least squares linear regression on the variable pairs $(\frac{1}{T}, E(T))$. This regression identifies $\beta_0$ and $\beta_1$, mathematically separating the serial and parallel workloads. We can then substitute $T = k\ell$ into the fitted model to accurately extrapolate the expected execution time $E(k\ell)$ for a target architecture where $k\ell \gg T_{max}$.

When fitting this regression model, it is critical to exclude measurements taken at complete hardware saturation (i.e., the benchmarking system's absolute maximum thread count $T_{max}$). At full capacity, execution time is artificially inflated by external systemic overheads, such as OS thread scheduling, memory bandwidth contention, and thermal throttling. Including this saturated data point warps the linear fit, systematically overestimating the serial fraction $f$ and severely degrading the accuracy of the large-scale extrapolation.

\subsubsection{Parameter Tuning}
To ensure our results are as replicable as possible, we did not want to include any parameters in our code. Instead, we have a root ``\texttt{params.toml}'' file which lists every value. At runtime these values are loaded by the benchmarking code, acting as a single source of truth for every test.

The file format supports multiple sets of parameters with different labels, and a particular parameter set can be loaded into any test or benchmark by using the \texttt{SPAR\_PARAMS=label} flag. We decided on a single set of parameters as a baseline for our testing in \cref{chp:results}, with any variation on this set included as its own complete set of parameters. The baseline parameters are labeled ``\texttt{standard}'' in \texttt{params.toml}, and is the default set used if no \texttt{SPAR\_PARAMS} flag is specified. To estimate the security of our parameters, we also include a simple ``\texttt{make estimate}'' command which reads this file and runs the lattice estimator \cite{cryptoeprint:2015/046} on each parameter set.
