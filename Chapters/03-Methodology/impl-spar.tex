\section{Implementation Details of sPAR}
\label{sec:impl:spar}
Our instantiation of \gls{spar} can be considered the \emph{minimal} version of the original specification~\cite{cryptoeprint:2025/860}. We do not consider the active threat model(s) of sections 6 and 7. Bucket sorting is also not implemented, though this should have a negligible effect as we estimate each bucket can be sorted in parallel in around $100$~ms~\cite{cryptoeprint:2025/860}. % , cryptoeprint:2024/1894

\begin{itemize}
    \item Uses a procedural programming paradigm, meaning the library implements the required functions but does not provide a full state-maintaining implementation of the server nor client. 
    \item The benchmarks and testing framework is what actually composes the protocol, using the functions from this library.
    \item This was done so that the functionality is not tightly coupled to the benchmarking without spending time implementing actual communication which would require additional work: serializing data, error handling, and coordinating multiple machines. % Basically: justify not having a compiled executable "server" and "client"
\end{itemize}

\subsection{Server Write Step}
The \texttt{Server::Write} deviates slightly from~\cite[Algorithm 2]{cryptoeprint:2025/860}. 

%% TODO: Explain the namespace::function naming convention, i.e. server::Write instead of "Server: Write" maybe even adopt this in the sPAR prelims.
\begin{itemize}
    \item Most important algorithm; does the actual homomorphic sorting
    \item Changes:
    \begin{itemize}
        \item Splits the write step and pre-processing step, the clients perform the pre-processing (making client::encryption slower) since we do not consider bandwidth optimizations
        \item HasWrite is inverted i.e. ``notHasWrite'' -> Saves one operation
        \item Uses external products to handle deep circuits as \cite{cryptoeprint:2025/860} recommends. In fact, their algorithm is general and ours is not; explicit external products.
        \item Not implementable using only external products per se: must use internal products
        \item To minimize noise and make initialization of the state matrices faster, the server can opt to init with "noiseless" encryptions. These provide no security on their own (which is fine since the initial state is known to all), but become regular encryptions after 1 iteration of the inner loop.
        \item Variables:
        \begin{itemize}
            \item $z_{i,d},\; I_{i,k},\;\mathsf{hasNotWritten}$ are $ \Call{RGSW}{m}, m \in \{0, 1\}^{N}$
            \item $L_{i,k} = \Call{RLWE}{m}, m \in R_t$
        \end{itemize}
    \end{itemize}
    %% TODO: Do not frame it as a mistake but rather as them using homomorphic multiplication in alg 2 and we using external products
    \item Order matters: swapping order so $h = (\mathsf{hasNotWritten} \boxtimes I_{i,k}) \boxtimes z_{i,d})$ saw a 30 to 40 bit improvement in the noise of \Call{Server::Write}{}
\end{itemize}

\begin{algorithm}
\caption{\texttt{Server::Write}}
\label{alg:spar:write}
\begin{algorithmic}[1]
\Require Reference to state matrices $I$ and $L$
\Require Encrypted RLWE value $V_r$
\Require Vectors $z_0$, $z_1$ and $z_2$ where $z_j$ is a vector of $\eta$ encrypted RGSW ciphertexts (TODO: explain one-hot encoding; only one of them, the elements of $z_i$ are 1 and the rest are 0) % $\{c_{j,0}, \dots, c_{j,\eta -1}\}$ for $j \in [0, 3)$ (one-hot encoding)
\Ensure Updates the state matrices $I$ and $L$
\Ensure Encrypted boolean indicating wether the operation was successful
\State $\mathsf{hasNotWritten} \gets \Call{EncryptRGSW}{1}$
\For{$d \gets \{0, 1, 2\}$} % [0, D) 
    \For{$k \gets \{0, 1, 2\}$}
        \For{$i \gets [0, \eta)$}
            \State $h \gets (\mathsf{hasNotWritten} \boxtimes I_{i,k}) \boxtimes z_{i,d})$
            \State $L_{i,k} \gets L_{i,k} + V_r \boxdot h$
            \State $I_{i,k} \gets I_{i,k} - h$
            \State $\mathsf{hasNotWritten} \gets \mathsf{hasNotWritten} - h$
        \EndFor
    \EndFor
\EndFor
\State \Return $\mathsf{hasNotWritten}$
\end{algorithmic}
\end{algorithm}

\begin{remark}
    From a programming perspective, the choice of $K = 3$ and $D = 3$ is arbitrary. The library allows a developer to configure different values for $K$ and $D$ as compile-time constants, with no impact on the size of the compiled binary/program. They are implemented as C++ generics, also known as template specialization.
\end{remark}
