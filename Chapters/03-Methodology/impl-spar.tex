\section{Implementation Details of sPAR}
\label{sec:impl:spar}
Our instantiation of \gls{spar} can be considered the \emph{minimal} version of the original specification~\cite{cryptoeprint:2025/860}. What is implemented is the core protocol against a passive adversary, covering setup, encryption, the write step, and partial and final decryption. We do not consider the active threat model(s) of sections 6 and 7, nor the recipient-anonymity layer, which is an ordinary encryption of the message before it enters the system and is therefore orthogonal to the \gls{fhe} pipeline. Bucket sorting is also not implemented, though this should have a negligible effect as we estimate each bucket can be sorted in parallel in around $100$~ms~\cite{cryptoeprint:2025/860}. % , cryptoeprint:2024/1894

The client-side functions require no new cryptography. The \texttt{client::Encrypt} function produces the message ciphertext and the index vectors under the joint key, and \texttt{client::Decrypt} produces a partial decryption; both are thin wrappers around the multi-party interface of OpenFHE described in \autoref{sec:mpfhe}, as is the server's final decryption \texttt{server::Decrypt}. The weight of this section therefore falls on the write step, which is the only part of the protocol that required new machinery.

One consequence of leaving the placement to the clients is visible in what they transmit. Since the server never evaluates the binary tree, clients send the full $\eta$-entry indicator vectors rather than the $\log\eta$ encrypted index bits, which costs bandwidth but no computation. We consider bandwidth out of scope, and note only that the tree would otherwise run on the server, where it is parallel across buckets.

\subsection{Server Write Step}
Function names in this chapter follow a \texttt{namespace::function} convention matching the source code \cite{gitrepo}, so \serverWrite{} denotes the implementation of the phase presented as \emph{Server: Write} in \autoref{sec:spar:protocol}. It deviates slightly from~\cite[Algorithm 2]{cryptoeprint:2025/860}. The first change is structural. The placement of \cite[Algorithm 2]{cryptoeprint:2025/860} is split out of the write step and moved to the client, so \serverWrite{} receives the indicator vectors ready-made and its own body is the second of the paper's two loops.

The remaining changes concern the homomorphic operations themselves. The paper writes $\mathsf{HomPlacing}^*$ for a generic homomorphic multiplication, which keeps it independent of any scheme; our version is the opposite, and names the specific product used at every step. Typing the operands as in \autoref{sec:spar:requirements} shows that the external product alone does not cover the circuit. Both $\mathsf{notHasWritten}$ and $I_{i,k}$ are \gls{rgsw} ciphertexts carrying state accumulated by earlier iterations, so the two products that form $h$ must be internal products, and only the application of $h$ to the message is external. Where the two products of $h$ are formed, the order of the operands is chosen so that the accumulated flag stays on the left and the freshly received $z_{i,d}$ enters on the right, which is the favourable case of \autoref{rem:extprod-asymmetry}.

Inverting the flag saves one operation per iteration. The paper multiplies by $(1 - \mathsf{hasWritten})$, whereas tracking the complement $\mathsf{notHasWritten}$ lets the flag be used directly and subtracted when a slot is claimed. The returned value inverts with it, so the function reports failure rather than success.

Finally, the initial state is not encrypted. The matrices $L$ and $I$, and the flag $\mathsf{notHasWritten}$, are constructed in the correct ciphertext form but with zeroed polynomials in place of a mask, which provides no security on its own. This is harmless because the initial state is public knowledge, and after a single product every entry is an ordinary ciphertext again. Avoiding the encryptions makes the setup considerably cheaper and starts the computation at a marginally lower noise level.

The operands of \autoref{alg:spar:write} are typed accordingly. The indicator entries $z_{i,d}$, the availability entries $I_{i,k}$ and the flag $\mathsf{notHasWritten}$ are all $\Call{RGSW}{m}$ with $m \in \{0,1\}^N$, while the accumulator entries $L_{i,k}$ and the message $V_r$ are $\Call{RLWE}{m}$ with $m \in R_t$.

\begin{algorithm}
\caption{\protect\serverWrite{}}
\label{alg:spar:write}
\begin{algorithmic}[1]
\Require Reference to state matrices $I$ and $L$
\Require Encrypted RLWE value $V_r$
\Require Vectors $z_0$, $z_1$ and $z_2$, where $z_d$ holds $\eta$ RGSW ciphertexts where exactly one entry encrypts $1$ and every other entry encrypts $0$
\Ensure Updates the state matrices $I$ and $L$
\Ensure Encrypted boolean $0$ if the operation was successful % value was placed and $1$ if every candidate slot was occupied
\State $\mathsf{notHasWritten} \gets \Call{EncryptRGSW}{1}$
\For{$d \gets \{0, 1, 2\}$} % [0, D) 
    \For{$k \gets \{0, 1, 2\}$}
        \For{$i \gets [0, \eta)$}
            \State $h\gets (I_{i,k}\boxtimes \mathsf{notHasWritten}) \boxtimes z_{i,d}$
            \State $L_{i,k} \gets L_{i,k} + V_r \boxdot h$
            \State $I_{i,k} \gets I_{i,k} - h$
            \State $\mathsf{notHasWritten} \gets \mathsf{notHasWritten} - h$
        \EndFor
    \EndFor
\EndFor
\State \Return $\mathsf{notHasWritten}$
\end{algorithmic}
\end{algorithm}

\begin{remark}
    From a programming perspective, the choice of $K = 3$ and $D = 3$ is arbitrary. The number of slots per bucket and the number of choices per client are implemented as C++ template parameters, and are resolved at compile time. % rather than carried as runtime values. Our build instantiates them only at $K = D = 3$, and supporting another pair requires nothing beyond adding the corresponding instantiation.
\end{remark}
