\section{(Somewhat) Practical Anonymous Router}
\label{sec:spar}
\gls{spar} realizes the anonymous router of \autoref{chp:background} from the primitives of the preceding sections~\cite{cryptoeprint:2025/860}. Each of the $\eta$ clients encrypts its message together with a randomly chosen destination index, and the server writes every message into an encrypted list at the position its sender picked. Both the list and the indices remain encrypted throughout the write.

%%
%% SYSTEM MODEL
\subsection{System Model}
\label{sec:spar:model}
The protocol runs in rounds between $\eta$ clients and a single server. Every client submits exactly one message per round, sending a random message if it has nothing to say, and all traffic passes through the server. The server is untrusted for privacy but trusted for availability, and may collude with any number of corrupted clients. Sender anonymity follows from the IND-CPA security of the underlying scheme, with definitions and proofs given in the original paper~\cite{cryptoeprint:2025/860}.

Two further assumptions are what the protocol takes explicit measures to satisfy. Messages are assumed to be uniformly distributed, which is what lets placement at a random encrypted index stand in for a shuffle. Messages sharing a bucket must additionally be sorted obliviously before the list is opened, since their relative order would otherwise reveal which sender wrote first.

%%
%% THE PROTOCOL
\subsection{The Protocol}
\label{sec:spar:protocol}
A one-time setup is followed by polynomially many rounds under the same keys, each consisting of four computations separated by two client--server round trips.

\subsubsection{Setup}
The clients agree on a set of \gls{FHE} parameters and run the multi-party key generation of \autoref{sec:mpfhe}, producing a joint public key under which every round is encrypted. % In contrast to existing protocols, neither a permutation nor any trusted party enters the setup.

\subsubsection{Client: Encryption}
Client $i$ encrypts its message under the joint key and samples three bucket indices $a_0, a_1, a_2 \overset{\$}{\leftarrow} [0, \eta)$ uniformly, encrypting the $\log\eta$ bits of each index separately. A single index per client would collide too often, whereas with $\eta$ buckets of three slots the probability that all nine candidate slots are taken falls below $10^{-11}$, and on that event the message is dropped and retransmitted in a later round~\cite{cryptoeprint:2025/860}.

\subsubsection{Server: Write}
The server keeps a message matrix $L$ of $\eta\times3$ \gls{rlwe} slots and an availability matrix $I$ of $\eta\times3$ encrypted flags marking which slots are free. For each client it evaluates \autoref{alg:spar:homplacing}, where a binary tree of depth $\log\eta$ turns each encrypted index into an indicator vector over the buckets, and the write loop then places the message in the first free slot among the three chosen buckets, tracked by the encrypted flag $\mathsf{hasWritten}$. Clients upload \gls{rlwe} ciphertexts only, as the index bits are expanded to \gls{rgsw} by the server~\cite{chillotti:onionring:2019, park:sortinghat:2022}.

Once all $\eta$ messages are written, the slots of each bucket are sorted obliviously and $L$ is broadcast to the clients.

\subsubsection{Client: Partial Decryption}
Each client partially decrypts all $3\eta$ slots with its own share (\autoref{sec:mpfhe}) and sends the result back to the server. % When $N > 3\eta$, the partial decryptions of one client pack into a single ciphertext~\cite{cryptoeprint:2020/015}.

\subsubsection{Server: Final Decryption}
The server aggregates the partial decryptions of each slot (\autoref{sec:mpfhe}) and recovers the list. Empty slots decrypt to zero and are discarded, leaving the $\eta$ messages in an order that is a fresh uniform permutation of the senders.

%% REQUIREMENTS
\subsection{Requirements}
\label{sec:spar:requirements}
\autoref{alg:spar:homplacing} is stated for a generic homomorphic multiplication, but the circuit it describes is deep. Every level of the binary tree multiplies the running node by a further encrypted bit, and the write loop chains $9\eta$ multiplications through $\mathsf{hasWritten}$ for each message. Ciphertext multiplication in the sense of \autoref{sec:bgv} would exhaust the noise budget long before a round completed, so the authors propose evaluating the tree with the external product of \autoref{def:prod:external}, whose noise grows additively along such a chain (\autoref{rem:extprod-asymmetry}).

The scheme underneath must therefore supply \gls{rgsw} ciphertexts and the external product, multi-party key generation and decryption, and a noise budget large enough to finish a round without bootstrapping. All three are native to TFHE, where the gadget is a digit decomposition of ciphertext coefficients. None are exposed by a BGV-\gls{rns} implementation, whose ciphertexts exist only as residues.
