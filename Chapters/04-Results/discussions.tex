\subsection{SIMD Packing}
Throughout this thesis we have emphasized that our implementation supports \gls{simd} packing, but nowhere in \gls{spar} is this utilized. The \texttt{server::Write} loop is the most computationally expensive part of the whole protocol. \gls{simd} packing allows the server to perform $N$ rounds simultaneously, making the \textit{per-round} times $N$ times faster, but converting this into higher throughput would require significant changes to the protocol. If $N$ rounds are performed then every client would presumably be encrypting, sending and partially decrypting $N$ times more data, requiring significantly higher bandwidth and RAM on the server.

% Enabling \gls{simd} presents another problem for \gls{spar}, since it requires $t$ to be a prime such that $t \equiv 1 \pmod{2N}$. The smallest such prime is $t = 65537$ for the other parameters of \autoref{tab:bench:params}. This is problematic since the $h \gets I_{i,k}\boxtimes\mathsf{notHasWritten}\boxtimes z_{i,d}$ assignment has only a single fresh ciphertext, $z_{i,d}$, meaning a ``dirty'' ciphertext necessarily must appear on the right hand side in one of the internal products, breaking the noise asymmetry from \autoref{rem:extprod-asymmetry}. We found that using this larger $t$, the \gls{spar} protocol was only able to support $\eta=3$ users.
