\section{Discussions}
\label{sec:results:discussion}
The results are slower than anticipated. Even though we are using much larger parameters than the small TFHE parameters suggested in~\cite{cryptoeprint:2025/860}, the protocol is an order of magnitude slower than what would be practical for most applications. In theory, an arbitrary number of users can be supported, but the parameters that make it possible are too slow for it to be practical in large networks. In the remainder of this section we discuss some potential optimizations that could improve the performance of \gls{spar} and make it feasible in more applications. %% TODO: Lay foundation by saying for example 'making it practical only for applications that can accept such a delay'

\subsection{AVX512 Instruction Set}
\label{sec:avx512}
OpenFHE supports the AVX512 instruction set through the Intel HEXL backend, which offers true \gls{simd} vectorization into 512-bit registers. The benefit offered by this acceleration is substantial. We were unfortunately not able to use AVX512 for our benchmarks due to hardware incompatibility, and stress that the benchmarks would be improved on equivalent but 512-bit capable hardware --- though by exactly how much remains to be seen.

Taking full advantage of AVX512 would require revisiting the parameters, since utilization depends on the sizes of the \gls{rns} moduli. A 512-bit register can for example hold eleven 42-bit integers together with one 50-bit integer, or twelve 42-bit integers with some bits left unused. Optimizing parameters for this scenario, and quantifying the improvement is left as future work.

\subsection{SIMD Packing}
\label{sec:simd-packing}
Throughout this thesis we have emphasized that our core library supports \gls{simd} packing, but nowhere in \gls{spar} is this utilized. The \serverWrite{} loop is the most computationally expensive part of the whole protocol. Since this function evaluates a binary tree, only the first slot is ever used. In theory, \gls{simd} packing thus allows the server to perform $N$ rounds simultaneously by packing one round into each slot of a ciphertext. It remains to be seen if this leads to higher throughput, or if the additional data transmitted slows down the server an equivalent amount.

A factor in this case is the sheer amount of data being handled. If $N$ rounds are performed then every client would presumably be encrypting, sending and partially decrypting $N$ times more data, requiring significantly higher bandwidth and RAM on the server. Each message already carries $32\text{ KiB}$ of data, and the \gls{rgsw} ciphertexts are far larger ($2k\ell \cdot 2N\log(Q) \text{ bits} \approx 48.16896 \text{ MB}$). Just storing the $N\cdot\eta$ encrypted messages $V_r$ and $3N\eta\log{\eta}$ encrypted bits $A_{i,d}$ as \gls{rlwe} ciphertexts would require almost $ \text{315 GB}$ of memory even for just 2 users. More realistically, a few ($\ll N$) rounds could still be run simultaneously with this approach.
